# V4.1 decode roadmap — 2026-09-18

Supersedes the priority ordering in `DECODE_PLAN.md` / `DECODE_TO_30_BRIEF.md`.
Everything here is either MEASURED today on live agent traffic or explicitly
marked as an estimate. The "ruled out" section exists because most of these have
been re-litigated across several sessions.

## Where we are

Production: V4.1-Flash MXFP4, `--ctx 307200`, `V41_CANDIDATE_POOL=1`, two boxes.

| workload | ms/token | aggregate |
|---|---|---|
| one agent, 85–221K ctx | 85–92 | ~11–12 tok/s |
| **50 concurrent agents** | **96–127** | **7.0 tok/s** |

Concurrency today makes each token *slower*, because 50 conversations compete for
one 4,454-slot expert pool: decode hit 0.9873–0.9898 → **0.9653–0.9810**, box-1
misses/token 1.23–1.47 → **1.42–3.37**. At ~9 ms/miss that is ~30 ms/token of
paging against ~12 before, which accounts for nearly all the degradation.

**Serialised concurrency is the worst of both worlds**: full cache pressure, zero
batching benefit.

## Where a ~100 ms token goes

`DEEPSTRIX_TOKEN_PROFILE=1`, one live token at 85K, 40 layers:

```
 24.84 ms  40x  igpu  igpu.moe.wait
 21.42 ms  40x  dgpu  dgpu.peer_push_ffn_input_norm.wait
 18.29 ms  40x  igpu  igpu.routed_moe
 11.31 ms  40x  igpu  igpu.peer_push_ffn_moe.wait
 10.45 ms  40x  dgpu  dgpu.ffn_combine.wait
  6.69 ms  40x  dgpu  dgpu.output_proj
  4.67 ms  40x  dgpu  dgpu.q_chain
  3.92 ms  40x  dgpu  dgpu.shared_expert
  3.36 ms  40x  dgpu  dgpu.kv_chain
  2.30 ms   8x  dgpu  dgpu.indexer
```

Real compute ≈ 47 ms (dGPU ~33, iGPU ~18); the rest is two halves handing off 40
times. Attention is not in the top 18 (`attn_compute` ~0.32 ms). **Do not**
conclude "handshakes are the bottleneck" from this — a `.wait` contains the
peer's compute, so summing waits double-counts. Separating real waiting from
submission lag needs the spans on one clock; that timeline is not built yet.

## Priority

### 1. Multi-stream decode (S≈8) — 3–4x, the only large win
Measured case above. The per-step costs that do **not** scale with S: 16.4 ms
link latency (205 µs × 80 calls), ~10 ms handshakes, the dGPU's projection GEMVs
(weight-bandwidth-bound, re-read nothing at B=4). Pick-trace sim says misses/token
rise only **9–17% at S=4–8** because a layer's expert union dedups *within* a
step — i.e. less cache pressure than serialised concurrency already pays.

Machinery that already exists: `submit(layer, b, xq, sel, ew, …)` is per-row;
`ExpertPager::ensure_batched`; `BatchScratch` at `B_MAX=1024`; the DSpark verify
is already a layer-major batched driver; `publish_pos_slot` exists precisely for
that ordering. Missing: S resident `HetModelState`s (228 MB each at 64K, 895 MB
at 307K, against 4.7 GB free dGPU), per-row attention against different KV
caches, a scheduler in `engine_worker.rs` (today `worker_loop` blocks per
request), and chunked prefill so a newcomer doesn't stall decoders.

**Blocker:** `VERIFY_DISAGREES_WITH_DECODE.md` — 45% argmax disagreement at B=6,
cause unknown, same machinery. But multi-stream gives a cleaner probe than we've
had: run S=2 with two *identical* sequences, each with its own KV, so every
confound from shared-window/rollback is gone. Rows must be bit-identical.

### 2. Link + hop latency — up to ~15 ms/token, pending one measurement
`link_us` is 252–267 µs at b=1. A minimal C echo over the same link with the same
socket options is **16.6 µs** (64 B) / **40 µs** (real 5 K/20 K shape). Box 2's
unbracketed path is only ~32 µs. So ~195 µs is unaccounted and most of it must be
box 1's client side. Instrumented in `56b0319` (`remote.hop.summary`); **not yet
run** — needs a restart. If the hops are ~20 µs each the fix is to write and read
on the calling thread (`wait()` blocks anyway; a 5 KB write cannot stall a 4 MB
send buffer).

Note this whole term is B-invariant, so multi-stream amortises it to ~2 ms/token
at S=8 for free. Worth doing for the S=1 interactive case, not worth weeks.

### 3. Box 2 fixed cost — ~4–5 ms/token, small safe changes
From the audit (`remote_experts.rs`, daemon half):
- **LRU is O(n) at 6,160 entries** (`iter().position()` ≈3,080 compares +
  `VecDeque::remove` ≈1,540 moves, ~6×/request). Est 1.2–2.0 ms/token; the only
  item big enough to explain the ~41 µs residual in the 105 µs fixed cost.
  Confirm with a targeted timer first.
- **Three blocking `hipMemcpy` for one 5,888 B payload** (2563–2565) = 46 µs,
  3× the blocking-copy floor. Frame is already contiguous and 8-aligned → one
  copy, three views. ~2.4 ms/token.
- **`SO_BUSY_POLL=500` buys nothing** — reader burns 526 µs CPU/request yet still
  sleeps ~1×/request (inter-frame gap ~1,250 µs). Raise above the gap or zero it.
- Cheap: `env::var("V41_B2_DBG")` per request (3117, not short-circuited, all its
  siblings are `LazyLock`); unbounded `tx_written` (~459 k undrained) and a
  `Vec<RequestRecord>` that reached 1,088,120 entries ≈ 90 MB; a 21 MB
  `AlignedBuf` alloc when the recycle pool is empty.

### 4. Expert format — the only path to 100 tok/s, gated on quality
Roofline: 4.51 GB of expert weights per token ÷ ~400 GB/s ≈ 89 tok/s single-stream
ceiling. At S=8 the union gives ~103 tok/s — i.e. **100 sits exactly on the
memory roofline with the current format, with zero margin**, and the disk needs
~6.3 GB/s sustained against ~6.9 available.

A Q2-class format (~175 GB) is 100% resident across our 217 GB — paging
disappears entirely and bytes/token roughly halve, putting 100 at ~half roofline.
User has rejected Q2 on quality. **The gating instrument is the CPU-oracle
surprisal scorer** (not built): score reference-model surprisal on our own
generated tokens, which settles both the quant question and §1.5's fidelity
impact with one tool.

## Ruled out — do not re-litigate without new evidence

| claim | verdict | evidence |
|---|---|---|
| custom Thunderbolt kernel driver, "10× latency" | **wrong layer** | raw echo 16.6 µs vs 205 µs paid; a perfect driver recovers 8% |
| gather instead of mask at layers 24/28/32/36 | **~1%** | `dgpu.indexer` = 2.30 ms/token; the "16.6 ms / 500× off roofline" comment is stale, WMMA fixed it |
| prefetch by prediction | **impossible** | prev-token 29.2%, union-16 68.3%, global top-128 89.6% — all below LRU's 97.75% |
| better replacement policy / bigger pool | **≤0.28pp** | LRU 2.247% vs frequency oracle 1.965%; 2Q is *worse* |
| hot-expert pinning | **no hot set** | top-16 = 0.6% of accesses |
| rebalancing the box1/box2 partition | **already optimal** | 0.397 == ideal shared pool exactly; hand-setting 0.50 → 4.03% |
| moving the dGPU to box 2 | **~1 ms** | 16.4 ms link latency is fixed regardless of which box is remote; split is pinned by RAM, not topology |
| DSpark for concurrent subagents | **dominated** | spends B=5 of expert reads for E≈2.9 tokens; 5 real streams yield 5 |
| "long-context falls off" / depth tax | **does not exist** | 4.5× context drop, no change in ms/token |
| "friend gets 15 tok/s on 128 GB, we're slower" | **different model** | ds4 has NO ROCm V4.1 path; those numbers are V4-Flash q2, 1.83 GB/token fully resident vs our 4.51 GB paging. Normalised we move 2× their bytes/s |

## Open questions

1. **Box-1 hop split** — instrumented, needs one restart. Decides whether item 2
   is 15 ms/token or 2.
2. **The critical-path timeline** — kernels, link and disk on one clock. Half of
   a 100 ms token is currently in `.wait` stages that cannot be attributed.
3. **dm-crypt's actual tax** — never measured. `dd iflag=direct` on the raw
   `/dev/nvme*` bounds it in ~20 min on a quiet box.
4. **B>1 fidelity** (`VERIFY_DISAGREES_WITH_DECODE.md`) — gates item 1.
5. **CPU-oracle surprisal scorer** — gates item 4.

## Process notes from today

Three outages, all mine, all the same shape: changing a bound or a hot path and
validating in a configuration unlike production. What worked was the opposite,
three times — proving `cap_covers_the_shipped_ctx` failed at the old value before
trusting it; the echo benchmark answering the driver question in an hour; and
`dgpu.indexer = 2.30 ms` saving us from building gather for 1%.

**Price the part before optimising it.** Every item above has a number attached
for that reason.
